Running GR00T N1 closed-loop in Isaac Lab 3.0

A 2-billion-parameter humanoid model and a simulator that can't live in the same Python process. Here's the bridge I built between them, and why I added a robot that deliberately does nothing.

Nov 2026·5 min read·Status: integration runs end to end
TL;DR
  • Goal: evaluate a released VLA checkpoint by letting it act in simulation, not just scoring it offline.
  • Isaac Lab 3.0 needs Python 3.12 and GR00T N1 needs 3.10, so they run as two processes joined by a small localhost bridge.
  • The bridge sends JSON plus numpy arrays loaded with allow_pickle=False, so no code can travel over the socket.
  • A hold-pose baseline measures the simulator's own cost before any slowdown gets blamed on the model.

Offline scores aren't the whole story

A lot of policy evaluation happens offline: compare predicted actions with recorded ones and compute an error. But a policy that's slightly off at every step can drift into states it has never seen, and offline numbers won't show that. The honest test is closed-loop: the model sees a frame, acts, the world changes, and it has to deal with the consequences. So I wanted NVIDIA's GR00T N1 driving the GR1-T2 humanoid inside Isaac Lab, on its manipulation tasks such as nut pouring and exhaust-pipe handling.

The obstacle: two Pythons

Isaac Lab 3.0 runs on Python 3.12. GR00T N1 needs its own Python 3.10 environment. You can't import both into one process, and forcing one stack onto the other's version is a fight you lose slowly. So I split them:

Two processes, one tiny protocol between them.

The bridge, kept deliberately small

bridge.py is the whole protocol. Each message is an 8-byte length header, then JSON metadata, then numpy arrays in .npz format. Two design choices mattered:

  • Only the standard library and numpy. That's what lets the same file import cleanly in both environments. Any heavier dependency would have tied it to one side.
  • No pickle. Arrays are loaded with allow_pickle=False. Pickle can run arbitrary code on load, so the bridge only ever carries data, even on localhost.

Matching the model's expectations

A VLA is sensitive to how its images are prepared, and a silent mismatch here makes a good model look bad. The GR1-T2 head camera produces 160×256 frames. The server zero-pads them to 256×256, matching the preprocessing in NVIDIA's reference IsaacLabEvalTasks. The model then returns a 16-step action chunk. A flag sets how many of those steps run before asking for a new chunk, which is the trade-off between reacting quickly and acting smoothly.

The robot that does nothing

The runner has a --policy hold mode that keeps the robot perfectly still. That sounds useless, but it answers a question that comes up as soon as things feel slow: is it the model or the simulator? A humanoid scene with rendering has a real cost of its own. Measure that first with the model out of the loop, and you know how much of any slowdown inference actually adds.

# 1) policy server, in the GR00T environment
python gr00t_server.py --model_path <checkpoint>

# 2) simulator-only baseline: no model involved
./isaaclab.sh -p run_isaac_gr00t.py --policy hold

# 3) closed loop
./isaaclab.sh -p run_isaac_gr00t.py --policy gr00t \
    --task Isaac-NutPour-GR1T2-ClosedLoop-v0 --episodes 3 --chunks 30

Where it stands, honestly

The loop runs end to end. I haven't published success rates yet, and I won't quote any until they come from fixed seeds with confidence intervals. Next:

  • Success rate per task over fixed seeds, with intervals.
  • How chunk length trades reactivity against success: execute 4 steps of each 16-step chunk, or all 16?
Most integration bugs don't crash. They quietly make a good model look bad. Small, checkable pieces are how you catch them.
