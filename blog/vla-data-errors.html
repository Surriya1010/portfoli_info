Which data errors break a robot policy?

Real robot data is always slightly wrong. I'm designing a study that measures which kinds of wrong actually matter, in simulation, where the truth is known.

Nov 2026·7 min read·Status: setup, no results yet
TL;DR
  • Take clean Franka demonstrations from LIBERO, add one realistic error type at a time at controlled strengths, fine-tune the same SmolVLA on each copy, and measure the drop in task success.
  • Three error types first: action/observation time offset, wrong task labels and operator jitter.
  • The study also asks whether cheap, label-free checks can catch each error before any GPU time is spent on training.
  • Everything runs on one 8 GB laptop GPU. No experiment has run yet; this post is the design.

The problem nobody can measure on real data

Every real robot dataset carries small errors. Camera frames and joint readings are captured at slightly different moments. Episodes get saved under the wrong task name. Teleoperators move hesitantly or shakily. Everyone working with robot data knows this. What's missing is a way to say how much each of these costs.

On real data you can't answer that, because you never know the true values. You can't tell how far off your timestamps are, or how many labels are wrong. Simulation flips this around: if I start from clean demonstrations and inject the error myself, I know exactly where it is and how big it is. That makes it possible to measure cause and effect.

The study loop, repeated for each error type and strength.

Three questions

  1. Dose-response: for each error type, how does task success change as the error gets stronger?
  2. Ranking: under the same training budget, which error types cost the most?
  3. Detection: can simple checks that need no labels find each error, measured against errors I placed myself?

Timing offsets come up again and again as a real-data problem, but they're rarely measured on training data, so that's the most interesting one. Wrong labels are the language-side counterpart, which matters for a model that's conditioned on an instruction. Jitter is deliberately the boring one: earlier work has already shown that action noise hurts, so if my pipeline doesn't show that, the pipeline is broken. It's a built-in sanity check.

Keeping the comparison fair

An experiment like this falls apart if anything other than the data changes between conditions. So the training recipe is locked:

  • Every run starts from smolvla_base, never from the LIBERO checkpoint, which has already seen clean data.
  • Same suite, same episodes, same number of steps, same batch size, same seed. The budget is fixed once, before any corrupted run, and never touched again.
  • The baseline is my own clean fine-tune with that exact recipe, not the published checkpoint.
  • Evaluation uses the same execution horizon for every condition, because SmolVLA's LIBERO score moves a lot with it.

Designing around an 8 GB GPU

The hardware constraint shaped the whole study. I compared the VLAs with LIBERO checkpoints on the Hugging Face Hub. SmolVLA (450M parameters) was the only one that could also be fine-tuned in 8 GB. Models in the 3 to 7 billion parameter range, such as pi0.5, GR00T N1.6 and OpenVLA-OFT, are out of reach for training here. To fit, I scoped training and evaluation to one LIBERO suite, libero_object. I chose it because published models score highest there, so a clean policy sits well above zero and any damage from the errors has room to show.

The biggest risk is a clean baseline that barely works. If the clean fine-tune sits near 0% success, no error can visibly make it worse, and the whole study is inconclusive. So the protocol checks this first, and adjusts the budget or suite before running a single corrupted condition.

Detecting errors before training

Training is the expensive part. If a cheap check over the dataset can flag a problem first, that's worth a lot in practice. Three detectors, all plain numpy:

  • Lag estimator: finds the shift that best lines up the commanded arm motion with the motion that actually happens next. It targets the time offset.
  • Jitter score: the share of action energy at high frequency. It targets operator noise.
  • Stall runs: the longest stretch of near-zero motion, for operator hesitation. This one is reported but not injected.

Wrong task labels can't be detected from motion alone. I'm listing that openly as a gap rather than pretending a detector covers it.

Where it stands

The corruption and detector library passes 13 unit tests on synthetic episodes. The dataset-corruption script works on a small fake dataset in the LeRobot v3 layout, and the Isaac Lab Franka control part runs on the laptop. Next: install the LeRobot environment, check that the official checkpoint reproduces its published score, then run the clean control.

Rules I'm holding myself to

  • No number gets reported without the command, seed, dataset revision and episode count behind it.
  • Every success rate comes with a 95% interval. Overlapping intervals mean "no difference shown", not "no difference".
  • If an error type has no effect, that's a result. I'll report it along with the smallest effect the experiment could have detected.
The point isn't to prove that dirty data is bad. It's to find out which dirt is worth cleaning.
